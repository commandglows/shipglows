# Quality-first Core and continuation pilot

## Ready scope and authority

Align Core topology with the existing common policy; replace ambiguous reference
applicability with explicit triggers; distinguish bounded corrections from material
changes needing a ready spec; align unfinished-report choices with actual operator
decisions. Preserve the approved compact layout and all closure reflections.
No new router, help-next-outcome redesign, runtime deployment or token-ceiling waiver.
Existing local quality-priority edits and unrelated sync-script work are preserved.

Main owns Core, its maintenance pack, the stale lifecycle/delegation topology clauses,
reporting root/blocked leaf, affected existing tests and mapped documentation.
One worker owns new scenario declarations in the existing registry, a focused
test and a cold baseline evidence file. Independent final review is read-only.

## Scenario-first acceptance

- Exact low-risk correction: one owner, explicit authority, proportional proof,
  truthful completion report; no new spec/delegation merely due to skill invocation.
- Material semantic/routing/security change: ready spec, required approval,
  independent review and relevant lifecycle gates remain mandatory.
- Known authorized continuation: execute the next safe unit without asking to
  continue. Unknown target, new effects or missing operator decision: stop and ask.
- Externally blocked work without a choice: state evidence and recovery action;
  do not manufacture strategic alternatives or imply completion.

Compare decisions, stops and evidence before costs. Freeze before-edit text hashes
and comparable declared reads; extend scenarios through proof/report where possible.
Declarations are not observed executions or provider-token telemetry. Keep existing
ceilings unchanged and disclose the four pre-existing budget failures. Additional
context with demonstrated quality value is allowed by the approved pilot, but a
failed existing budget remains failed unless explicitly arbitrated.

Fresh external docs not needed: repository-owned normative behavior. Validate with
focused contract/negative tests, declaration checks, independent scenario review
and changed metadata. Update mapped skill-runtime documentation. Public invocation,
plugin distribution and editorial layout are unchanged; changelog internal-only.
