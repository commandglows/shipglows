# Immutable Short Domain Identifiers For Generated Code

## Title

Immutable Short Domain Identifiers For ShipGlows-Generated Code

## Status

Implementation, independent standard verification, and local closure are complete. The operator-approved doctrine now lives in the shared code-quality contract with scenario-first mechanical proof; Git shipping remains pending.

## User Story

As the ShipGlows operator, I want code authored or materially modified by skills to use short immutable domain identifiers for stable vocabularies, so data, integrations, translations, and migrations stay coherent without confusing domain identity with technical instance identity.

## Minimal Behavior Contract

When a ShipGlows skill creates or materially modifies a stable machine-readable domain vocabulary, it gives every shared concept a short, non-localized, immutable canonical code distinct from the display label and from each record's technical instance identifier. Once published, persisted, exported as a contract, or consumed by another surface, that code cannot be renamed or recycled. Evolution uses bounded input aliases, explicit lifecycle metadata, and an optional declared replacement; a retired concept with no successor keeps a reserved tombstone without `replaced_by`. Unknown, ambiguous, malformed, or colliding input fails observably and is never guessed from a localized label. During a legacy migration, aliases may remain readable for a bounded compatibility period, but all new writes and outputs use only the canonical code.

## Success Behavior

- Preconditions: a code change introduces or materially modifies a stable set of shared concepts such as formats, placements, categories, platforms, statuses, error types, or capabilities.
- Trigger: an implementation, fix, technical-audit, or verification skill applies the Clean Code contract to the affected surface.
- User/operator result: the solution and its proof explicitly distinguish technical instance ID, canonical domain code, and localized display label.
- System effect: each domain owns its canonical registry; storage, APIs, imports, exports, logs, and integrations use canonical codes, while the UI resolves mutable labels by locale.
- Success proof: the shared contract and its mechanical test cover `ID-LABEL-LOCALE`, `ID-ALIAS-MIGRATION`, `ID-DEPRECATE-REPLACE`, `ID-TECHNICAL-INSTANCE`, `ID-COLLISION`, `ID-UNKNOWN`, `ID-REGISTRY-OWNERSHIP`, `ID-ADDITIVE-MIGRATION`, `ID-AUTHORIZATION-BOUNDARY`, and `ID-EXTERNAL-MAPPING`.
- Silent success: not allowed; a non-trivial implementation records a proportional `Domain Identifier Gate` verdict in the same spirit as the `Clean Code Gate`.

## Error Behavior

- Expected failures: empty or malformed code, duplicate canonical code, alias-to-code collision, alias cycle, invalid or missing required replacement target, rename/recycle attempt, unknown input, machine comparison on a label, or destructive migration.
- User/operator response: the check, test, or report identifies the code, registry, and violated invariant; it never proposes guessing the concept from translated copy.
- System effect: no new write uses a legacy or localized value, and no migration removes the legacy read path before read compatibility, backfill, and migration proof are complete.
- Must never happen: use a UUID as a substitute for a shared vocabulary code, use a domain code as the unique identity of a record, recycle a published code, let alias normalization bypass access policy, or build a generic global registry that erases domain ownership.
- Silent failure: not allowed; a consumer that does not recognize a code either represents it explicitly as `unknown` when its forward-compatibility contract requires tolerance, or rejects it with an actionable error at a trust boundary. It never silently coerces the value.

## Problem

Without a shared doctrine, products and skills can represent the same concepts with labels, slugs, enums, UUIDs, or ad hoc strings. Renames, translations, and integrations then become fragile data migrations; machine comparisons depend on mutable copy; aliases remain output values indefinitely; and an old identifier can be recycled for a different meaning.

The rule must apply to code produced by ShipGlows without forcing a mass rewrite of existing repositories, replacing technical UUID/ULID identifiers, or creating an EAV-style universal registry that artificially centralizes every domain.

## Solution

Extend the shared `clean-code-quality-contract.md` with a scenario-first `Domain Identifier Gate`. The gate defines the `technical instance ID / immutable domain code / mutable localized label` separation, the minimum registry and entry metadata, canonical-code lifecycle, additive migration, and security boundaries. Strengthen the existing test so current consumers continue to load this doctrine without copying it into every skill.

## Scope In

- Formalize the rule for every new stable machine-readable vocabulary created or materially modified by ShipGlows.
- Define affected vocabularies: formats, placements, categories, platforms/channels, statuses, error types, capabilities, workflow actions, and other durable shared concepts.
- Preserve UUID/ULID or equivalent technical identifiers for records, events, jobs, sessions, files, and other instances.
- Define a short, ASCII, non-localized, readable, domain-prefixed canonical code unique within its registry, for example `FMT_REEL`, `PLC_REEL_COVER`, or `ERR_ASSET_ARCHIVED`.
- Separate the canonical code from localized labels, descriptions, slugs, and other mutable representations.
- Require registry-level `domain`, `namespace`, `owner`, and `version` metadata.
- Require entry-level `code`, lifecycle `status`, and `introduced_in`; allow localized labels and input aliases as presentation/compatibility metadata, and require `deprecated_in` plus optional `replaced_by` when an entry is deprecated or retired.
- Define input aliases, deprecation, optional `replaced_by`, tombstones, bounded compatibility policy, and the prohibition on recycling.
- Define registry ownership by domain with shared validation conventions.
- Define prospective adoption and additive migration for existing vocabularies touched by a change.
- Add mechanical protection to the Clean Code contract test.

## Scope Out

- Migrate every repository and existing enum in this chantier.
- Replace UUID/ULID, primary keys, or identifiers for jobs, events, sessions, files, or records.
- Impose one universal character count or a central database for all codes.
- Build a generic global registry, an EAV table, or a new runtime dependency.
- Modify consumer skills; they already load the shared Clean Code contract.
- Implement registries owned by ContentGlowz or another product in this ShipGlows chantier.
- Retroactively rename published codes or rewrite historical evidence.

## Constraints

- The doctrine lives at the highest reusable level and is not duplicated in every `SKILL.md`.
- A canonical code becomes immutable once published in an API, persisted, exported, logged as a contract, or consumed by another surface.
- The default format is ASCII uppercase with `_`-separated segments and a domain prefix. A project may retain an equivalent established convention only when the implementation records how it preserves stability, uniqueness, non-localization, and unambiguous ownership.
- `short` means concise and ergonomic for people and tools, not one arbitrary numeric limit shared by every domain.
- Outputs and new writes always use the canonical code; aliases are bounded read/migration mechanisms.
- Each alias has a declared compatibility owner and removal criterion; time alone does not permit removal without compatibility proof.
- A legacy migration remains additive and reversible until proof is complete; the first phase never deletes a column, value, or mapping.
- Permission, role, and capability codes never grant authorization by their shape alone; authoritative server-side access control remains mandatory.

### Scenario-first pressure scenarios

- `ID-LABEL-LOCALE`: changing `Reel`, `Reel video` or a French translation changes only the label; `FMT_REEL` remains the stored and exchanged value.
- `ID-ALIAS-MIGRATION`: a legacy input such as `reel` resolves to `FMT_REEL`, while the API, storage and export emit only `FMT_REEL`.
- `ID-DEPRECATE-REPLACE`: a retired code remains reserved, declares lifecycle metadata and may point to `replaced_by`; it is never reassigned to another meaning.
- `ID-TECHNICAL-INSTANCE`: two records of the same format have distinct UUID/ULID instance IDs while sharing `FMT_REEL` as their domain code.
- `ID-COLLISION`: duplicate canonical codes, alias collisions and cyclic replacements fail deterministically before generation or migration proceeds.
- `ID-UNKNOWN`: an unknown value at a trust boundary is rejected or represented explicitly according to the consumer contract; it is never guessed from a localized label.
- `ID-REGISTRY-OWNERSHIP`: format and placement domains keep separate registries and owners while sharing validation rules; no generic mega-registry is introduced.
- `ID-ADDITIVE-MIGRATION`: legacy values remain readable through bounded compatibility until backfill and proof permit retirement, while all new writes and outputs use canonical codes.
- `ID-AUTHORIZATION-BOUNDARY`: readable role, permission, or capability codes and their aliases never grant or widen access; authoritative server-side policy remains decisive.
- `ID-EXTERNAL-MAPPING`: vendor, generated, protocol-defined, and documented project-constrained identifiers retain their required form and map separately to a product-owned canonical domain code when product meaning is also needed.

## Edge Cases

### ZOMBIES coverage

- Z — Zero: empty, null, whitespace-only or missing codes are rejected; an empty registry is valid and creates no placeholder code.
- O — One: one canonical code resolves to one concept and may expose several localized labels without changing identity.
- M — Many: canonical codes remain unique across many entries; aliases resolve to exactly one canonical code; ordering never changes identity.
- B — Boundary Behaviors: unpublished draft codes may be changed before durable use, but published/persisted codes cross the immutability boundary; deprecated codes remain reserved after their active lifetime.
- I — Interface definition: registry, storage, API, import/export, UI, logs and migration tooling agree on the canonical wire value while labels remain presentation data.
- E — Exercise Exceptional behavior: malformed codes, unknown values, duplicates, alias collisions, cycles, invalid required replacement targets and partial migration fail observably without silent coercion or destructive cleanup.
- S — Simple Scenarios, Simple Solutions: use a small domain-owned registry and shared validation convention; do not add a universal registry service or speculative compatibility layer.

### Additional abuse and migration cases

- A translated label equals another concept's label: canonical codes keep both concepts unambiguous.
- A legacy alias equals another canonical code: validation blocks the registry before release.
- A deprecated code has no replacement because the concept is removed: retain a tombstone with no `replaced_by`; do not invent a replacement.
- A downstream consumer receives a newer code: its explicit compatibility policy chooses rejection or `unknown`; label fallback is forbidden.
- A code participates in access control: aliases may normalize input but cannot expand permissions or bypass the authoritative policy.
- Two domains want the same suffix: namespace prefixes and separate ownership prevent accidental semantic coupling.

## Risks

- Doctrine overreach: applying codes to every entity would duplicate UUID/ULID identity; mitigated by the explicit stable-vocabulary applicability gate.
- Premature centralization: a universal registry would erase domain ownership and create coupling; mitigated by domain-owned registries with shared conventions only.
- Migration risk: deleting legacy values too early could make stored data unreadable; mitigated by additive mapping/fields, bounded dual-read, backfill and proof before retirement.
- Compatibility drift: aliases could become permanent output values; mitigated by canonical-only writes/outputs and lifecycle metadata.
- Security risk: treating a readable permission code as authorization could enable access-control bypass; mitigated by authoritative server-side policy and explicit A01 gate.
- Maintenance risk: brittle tests could freeze wording rather than behavior; mitigated by asserting a small set of semantic markers and scenarios.
- Adoption risk: an all-repository rewrite would create large unsafe diffs; mitigated by prospective application and opportunistic migration when a vocabulary is materially touched.
