# Bug Record: BUG-2026-09-02-001

## Summary

A valid Flutter Windows native build can outlive the DevServer's fixed 90-second
readiness deadline. The DevServer then stops the still-live managed process and
records `error`, even though Flutter continues to report build progress. The
supervisor already supports authenticated hot reload, but the standard Windows
CLI has no explicit observable reload command.

## Reproduction

1. Start an attached Flutter Windows project whose native build exceeds 90 seconds.
2. Observe `daemon.connected`, `app.start`, and unfinished `app.progress` events.
3. Observe `Flutter supervisor timed out before app.started.` and registry `error`.
4. Run the same project build outside the supervisor and observe successful completion.

## Expected Behavior

- Live valid startup progress keeps the session in a bounded `building` or
  `starting` state until the matching `app.started` event arrives.
- A dead or silent supervisor still reaches a deterministic terminal timeout and
  its owned process tree is cleaned up.
- `s reload -ProjectPath <path>` targets only a ready managed Flutter session and
  reports a bounded success, failure, or unavailable result without stop/start.

## Observed Behavior

- A fixed readiness deadline converts an active native build into terminal error.
- Operators cannot explicitly invoke and observe the existing reload IPC through
  the standard CLI.

## Evidence

- Proof path: `regression-first`, followed by managed-runtime and physical retest.
- Project witness: ContentGlows Flutter Windows, read-only for this repair.
- Sensitive values are excluded; logs are represented only by protocol summaries.

## ZOMBIES Coverage

- Zero progress: deterministic silent timeout.
- One progress event: bounded extension, never unbounded liveness.
- Many progress events: rolling bounded lease with a hard startup ceiling.
- Boundary/interface: stale app IDs, readiness transition, IPC response schema.
- Exceptional: process death, malformed state, late response, stop during build.
- Simple: successful matching `app.started` and ready-session reload.

## Closure Criteria

- Automated readiness and IPC regressions pass for every accepted scenario.
- Other Flutter devices and non-Flutter DevServer paths remain unchanged.
- Linked runtime help exposes the exact reload command.
- A managed ContentGlows Windows session survives a long build and reflects a
  Dart change through reload without an explicit release build.
