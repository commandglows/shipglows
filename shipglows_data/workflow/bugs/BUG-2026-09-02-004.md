# Bug Record: BUG-2026-09-02-004

## Summary

A managed attached Flutter Windows cold start can complete the native build and
launch the application, yet lose the Flutter debug connection before the
matching `app.started` event establishes readiness. A retry can succeed without
any application-code change, which makes this a distinct intermittent startup
failure rather than a recurrence of the progress-aware timeout defect.

## Reproduction

1. Start a managed attached Flutter Windows session from a cold state.
2. Allow the native build to complete and the application process to launch.
3. Observe that Flutter loses the debug connection before emitting the matching
   `app.started` event.
4. Stop or clean up the failed managed session, then repeat the same start.
5. Observe that a subsequent attempt may reach `app.started` and `running`.

## Expected Behavior

- A successful build and launched Windows runner establish a stable Flutter
  debug connection and emit the matching `app.started` event.
- The registry remains `starting` until that event, then becomes `running`.
- If attachment fails, the DevServer records a precise terminal reason and
  cleans only the owned session process tree.
- Retrying does not require a release build or a modification to the witness
  application.

## Observed Behavior

- The first cold-start validation launched the Windows application but lost the
  Flutter debug connection before `app.started`.
- The second cold-start attempt succeeded and produced `app.started`.
- The resulting session was managed, attached, targeted `windows`, retained
  `flutterHeadless=false`, and was recorded as `running` without `lastError`.
- An explicit reload succeeded in 313 ms and reported `Reloaded 0 libraries`.

## Evidence

- Evidence type: operator-observed physical validation plus redacted local log
  summaries.
- Proof path: repeated managed Flutter Windows cold start followed by explicit
  reload on the successful session.
- Witness application: ContentGlows, used read-only; no project file was changed.
- Sensitive values, absolute user paths, process identifiers, application IDs,
  and raw logs are intentionally excluded.

## Constraints and Limits

- The original runner exit remains intermittent and its deeper platform cause is
  not proven; the repair therefore provides bounded recovery at the DevServer
  ownership boundary instead of claiming to prevent the runner exit itself.
- The automatic Dart file watcher was not exercised by this validation.
- A successful retry does not close the defect or establish a recurrence rate.
- ContentGlows is a read-only witness and must not be modified to mask the issue.

## Closure Criteria

- Repeated managed Flutter Windows cold starts establish the matching
  `app.started` event without intermittent debug disconnects.
- A forced or simulated pre-readiness disconnect produces a deterministic,
  actionable error and cleans the owned process tree.
- The registry never declares `running` before matching `app.started`.
- A successful attached session still supports explicit reload without native
  rebuild, device change, or session replacement.
- Focused regression tests and a physical Windows retest pass before closure.

## Next Step

Monitor future Flutter Windows cold starts for recurrence. If the runner exits
again, preserve the new terminal diagnostic so its deeper platform cause can be
correlated without reopening the already-correct timeout and reload behavior.
