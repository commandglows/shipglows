# Bug Record: BUG-2026-08-24-002

## Summary

The dependency setup transcript used Tee-Object -Append, which writes UTF-16LE under Windows PowerShell 5.1 and could mix that output with existing log bytes. The repaired writer starts each dependency attempt as UTF-8 without a BOM and preserves both console output and native exit-code handling.

## Reproduction

- Preconditions:
  - Windows PowerShell 5.1.
  - A project whose dependency setup writes through the DevServer setup-log path.
- Steps:
  1. Run the dependency setup path that records `setup.log`.
  2. Inspect the resulting bytes and decode the log as the runtime diagnostics reader does.
- Pre-fix result: a fresh-file reproduction emitted a FF FE BOM and 13 NUL bytes for two lines.
- Post-fix result: the dependency setup regression produces strict UTF-8 without NUL bytes under Windows PowerShell 5.1 and PowerShell Core 7.6.5.

## Expected Behavior

- `setup.log` uses one documented encoding, contains no NUL bytes, and remains readable by startup diagnostics.

## Observed Behavior

- Tee-Object -Append under Windows PowerShell 5.1 emitted UTF-16LE at the dependency-log boundary.
- Repeated dependency attempts could therefore retain or combine incompatible byte encodings in setup.log.

## Evidence

- Focused byte-level reproduction: a new log written by Windows PowerShell 5.1 contained a UTF-16LE BOM and NUL bytes.
- Automated retest: the repaired dependency path resets the current-attempt log to UTF-8 without a BOM, preserves non-ASCII text and console output, and retains failure-code behavior.
- No raw project log or credential-bearing content is retained in this record.
