# Bug Record: BUG-2026-08-23-002

## Summary

The Windows full installer treated any runnable managed Flutter SDK as permanently complete. Repeated installations therefore preserved an old detached commit instead of converging the ShipGlows-owned checkout to the current official stable revision.

## Expected Behavior

- Only `%LOCALAPPDATA%\ShipGlows\flutter` is eligible for automatic update.
- The ShipGlows source declares an exact validated Flutter/Dart baseline, fetches its commit as `origin/shipglows-stable`, and a local `stable` branch tracks that pinned ref.
- A non-official origin or tracked local changes stop convergence without overwriting work.
- Failed validation after checkout restores and revalidates the previous revision.
- Valid external Flutter SDKs are reused but never updated.

## Fix and Proof

The installer now implements that bounded transaction for both fresh and repeated managed installs. The exact Flutter 3.47.1 / Dart 3.13.1 baseline is source-controlled, so an ordinary installer rerun cannot silently move projects to a newly published Flutter release. Regression proof covers the existing-SDK path, pinned refspec, named branch, and automatic rollback. Live branch bootstraps converged the managed SDK to exact commit `6655482ec06e547f90abf8ae7590466f4415978d`, local branch `stable`, upstream `origin/shipglows-stable`, Flutter 3.47.1, and Dart 3.13.1. The tracked SDK tree is clean and `flutter doctor -v` reports no issues after environment refresh.

The application proof stopped safely at `flutter pub get --enforce-lockfile`: the current stable SDK would update seven SDK-coupled dependency versions. The command exited 65, the lockfile hash remained unchanged, and analyze/tests/build were not run.

## Next Step

Choose whether the application lockfile may be regenerated for current Flutter stable, then execute analysis, tests, and `flutter build windows`.
