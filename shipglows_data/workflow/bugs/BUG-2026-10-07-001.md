# Readwise OAuth callback port reserved by Windows

## Reproduction

Before the dynamic-port fix, run `shipglows readwise login` with Readwise 0.5.10 on this Windows machine.
The browser opens, then the provider reports `listen EACCES` on `0.0.0.0:6274`.
Expected: a usable authentication route with an actionable local failure.

## Diagnosis

The official provider fixes both its callback listener and redirect URI to
port 6274. Windows excludes that port even for loopback binding. This is an
OS reservation, not an occupied listener. No Windows reservation was modified.

## Historical Token Workaround

The first attempt tested token recovery without repairing browser OAuth.
At that stage the adapter checked the fixed port and offered `login --token`.
That command delegates to the official hidden prompt without passing a token
in arguments. Interactive `login-with-token` also works without an environment
token. Non-interactive input still requires the environment variable.

17 tests cover blocked and available callback ports, prompt delegation and
existing credential handling. On the installed Windows launcher, OAuth exits
before browser launch; the token path reaches the real hidden prompt and was
cancelled with Ctrl+C without entering a token.

## Current State And Remaining Proof

The maintained dynamic-port adapter has replaced the fixed-port precheck.
The local port fix and 25 tests pass; live client registration and opening the
authorization page are verified. Account authorization was not completed.
Live code exchange, official session reuse/refresh and library access remain
unverified. Status stays `fix-attempted` pending that external proof.

Resume with `shipglows readwise login` only when the operator resumes account
authorization. A token or purchase is not required to prove the local port fix;
do not automatically reopen browser attempts or assert current vendor pricing.

## Durable Resolution

Operator review: the token alternative is a workaround, not a durable OAuth fix.
The installed provider 0.5.10 hardcodes 6274 without a port setting. The maintained
`cli/readwise_oauth.py` now reserves 127.0.0.1:0 before browser launch, retaining
the listener until the complete attempt ends. It uses one actual redirect URI
for registration, authorization and exchange; a fresh registration replaces
the old fixed-port client only after successful authentication.

The adapter uses PKCE S256, random state, rejects mismatched/replayed callbacks,
allows HTTPS Readwise provider endpoints only, refuses HTTP redirects and never
prints provider credentials/errors or callback queries. A failed attempt keeps
the old session. It persists atomically in the official format, so the provider
retains command and refresh ownership. Installers include this maintained file;
there is no global-package patch to lose on reinstall.

25 automated tests pass. A live installed invocation reserved port 5223, completed
registration and opened the browser, proving the provider accepts that client
registration. No user callback arrived within two minutes, so the attempt ended
without changing the session. Live authorization/code exchange remain unverified.
Second installed invocation reserved port 2193 and opened the authorization page;
it also expired without callback. No account credentials were replaced. Do not
automatically reopen browser attempts while operator authorization is pending.
Operator clarification: the authorization page appeared, but account login was
not completed. Live authorization is deferred by the operator because of account
access requirements. This is an external validation limit, not another callback
port failure. Keep live session/code-exchange proof pending until authorization
is resumed; do not require a purchase merely to validate the local port fix.
